РАЗДЕЛ 1. СМЕТЫ: создание, синхронизация при заказах, история изменений
=================================================================
(записано 05.09.2026, по итогам разбора работы со сметами нестандартных
изделий новых (26) заказов - uOrders.pas, uFrmOWOrder.pas, d_orders.sql,
d_estimates.sql, uFrmOGedtEstimate.pas, uFrmOWrepEstimateChanges.pas)


1.1. Два разных вида сметы - смета-эталон и смета позиции заказа
-----------------------------------------------------------------
В таблице estimates запись всегда относится ровно к одному из двух объектов
(взаимоисключающе):
  - смета-эталон стандартного изделия      - estimates.id_std_item заполнен,
                                              id_order_item = null;
  - смета конкретной позиции заказа (слеша) - estimates.id_order_item
                                              заполнен, id_std_item = null.

Это ДВЕ РАЗНЫЕ записи с разными id, даже если по смыслу вторая - это просто
копия первой. Путаница "почему я отредактировал смету, а в истории/журнале
её не видно" почти всегда сводится к тому, что редактировалась одна запись
estimates, а смотрели/ждали изменений в другой (см. 1.5 и 1.6).

Состав сметы хранится в estimate_items (позиции сметы: группа, наименование,
единица, qnt1 - количество на единицу изделия, qnt/qnt_itm - пересчитанное
на количество в заказе/в ИТМ).

Признаки на estimates:
  - isempty = 1  - "без сметы" (отметка, что смета для этого изделия не
                   предусмотрена никогда, не путать с "ещё не загружена");
  - dt           - дата, проставляется КАЖДЫЙ раз при успешном сохранении
                   через TOrders.ApplyEstimateArray, даже если состав сметы
                   фактически не менялся (см. 1.7 - важная ловушка).


1.2. Стандартные и нестандартные изделия, старый и новый (26) формат заказов
-----------------------------------------------------------------------------
or_std_items.id_or_format_estimates определяет принадлежность изделия:
  - > 0   - настоящее стандартное изделие, входит в конкретный формат/
            подгруппу сметных эталонов (or_format_estimates);
  - -1    - нестандартное изделие ПРОИЗВОДСТВА (тип П) нового (26) формата;
  - -2    - нестандартное изделие ОТГРУЗКИ (тип О) нового (26) формата;
  - -3    - нестандартное изделие ПОЛУФАБРИКАТА (тип ПФ) нового (26) формата;
  - 0     - старый формат (до 26), нестандартное изделие без деления на
            группы (создаётся через старую p_CreateOrStdItem_Nstd).

orders.std_item_type (см. константы STDITEM_TYPE_PRODUCTION=0/
STDITEM_TYPE_SHIPMENT=1/STDITEM_TYPE_SEMIPRODUCT=2 в uOrders.pas) - тип
самого заказа. cOrderNew26TypeID - порог id заказов нового формата (заказы
с id >= этого порога считаются заказами формата 2026).

Новое нестандартное наименование в заказе типа П создаётся процедурой
p_create_or_std_item_nonstandard_new_format (d_orders.sql) и заводит СРАЗУ
ДВЕ парных записи в or_std_items:
  - группа -1 (id = p_id_item) - "эталон" для производства; смета к ней
    НЕ создаётся автоматически - её должен вручную заполнить пользователь
    (редактирование см. 1.4, редирект для типа П);
  - группа -2 - "эталон" для отгрузки этого же нестандартного изделия;
    для неё смета создаётся СРАЗУ и автоматически - из одной позиции,
    которая ссылается на изделие группы -1 (в количестве 1 шт., единица
    id_unit=1); эта смета предназначена только для копирования в позиции
    отгрузочных заказов и открывается только на просмотр (см. 1.4).
Для заказа типа О (отгрузка) своё нестандартное наименование завести
нельзя - допустимо только уже существующее (в паре) для родительского
производственного заказа (см. p_get_or_std_item_id_nonstandard_shipment).
Для типа ПФ (полуфабрикат) создаётся одна запись в группе -3, без пары.

ВАЖНО (исправлено 05.09.2026): order_items.id_std_item нестандартной позиции
ОТГРУЗОЧНОГО заказа должен ВСЕГДА указывать на группу -2 этого наименования,
а не на -1 (группу производства) - независимо от того, как позиция попала в
заказ. Раньше (см. TFrmOWOrder.SaveOrderItems, uFrmOWOrder.pas) резолвинг
id_std_item через p_get_or_std_item_id_nonstandard_shipment выполнялся ТОЛЬКО
если имя позиции менялось (IsNameChanged) - а при автосоздании отгрузочного
заказа на основании производственного (см. FCreateShipmentFromProductionId,
1.4b) состав копируется как отдельные НОВЫЕ позиции, но имя НЕ меняется, из-за
чего id_std_item копировался как есть с позиции производственного заказа,
т.е. оставался равен -1. Такая позиция навсегда оставалась привязанной к
чужой (производственной) группе - в т.ч. это ломало пересчёт смет по 1.4
(RefreshEstimatesToOrder брал бы для неё детальный эталон производства, а не
фиксированную "1 шт." отгрузки). Исправлено: резолвинг в группу -2 теперь
выполняется для ЛЮБОЙ нестандартной позиции заказа типа О нового формата,
даже если имя не менялось.

ЕЩЁ ОДНО ИСПРАВЛЕНИЕ (05.09.2026), там же рядом: автоматическая смета-ссылка группы -2 (см. выше -
1 позиция, кол-во 1, ссылка на изделие -1) раньше создавалась p_CreateEstimateItem вообще БЕЗ ГРУППЫ
(id_group передавался как null) и БЕЗ ПРЕФИКСА в наименовании (просто "голое" имя изделия). Правильно -
группа "Готовые изделия" (bcad_groups, у неё is_production = 1) и наименование с префиксом подгруппы -1
('НСТД.П_' || имя) - именно так, аналогично, эта смета-ссылка уже создавалась для НАСТОЯЩИХ стандартных
изделий (см. TFrmODedtOrStdItem.CreateSelfSmeta, uFrmODedtOrStdItem.pas) - там группа была захардкожена
в Delphi константой BCAD_GROUP_FINISHED_ITEMS = 104, а префикс вычислялся отдельной функцией
GetPrefixedName. Обе реализации (для стандартных и для нестандартных изделий) объединены в одну общую
хранимую процедуру p_create_shipment_estimate_from_production_item (d_estimates.sql) - группа ищется по
признаку bcad_groups.is_production (сейчас всегда = 1, но вынесено в параметр на случай появления в
будущем разных групп для стандартных/нестандартных готовых изделий), префикс - по or_format_estimates.
prefix переданной производственной подгруппы (для нестандартных изделий это подгруппа -1 = 'НСТД.П').

ДОИСПРАВЛЕНИЕ (05.09.2026): после внедрения p_create_shipment_estimate_from_production_item группа
проставлялась верно (104), но префикс в наименовании всё равно не появлялся никогда - ни разу, ни в одном
тесте. Причина - ошибка в самой процедуре (d_estimates.sql): условие вычисления итогового имени было
  v_pname := case when v_prefix is not null and v_prefix <> '' then v_prefix || '_' || p_production_name
             else p_production_name end;
а в Oracle пустая строка '' - это NULL, и сравнение любого непустого значения с NULL через <> всегда даёт
NULL (не TRUE) - поэтому вся ветка THEN была НЕДОСТИЖИМА, CASE всегда уходил в ELSE, и префикс не
подставлялся никогда, даже когда v_prefix успешно находился (что и сбивало с толку при диагностике -
изолированный select prefix отрабатывал верно, группа тоже была верна). Исправлено - лишняя проверка
<> '' убрана, оставлено только v_prefix is not null.


1.3. Когда вообще происходит синхронизация смет заказа
---------------------------------------------------------
Точка входа - TFrmOWOrder.SaveEstimates (uFrmOWOrder.pas), вызывается при
каждом сохранении заказа (кроме шаблонов и удаления):
  - если статус заказа "Запущен" или "Утверждён" (ORDER_ID_STATUS_STARTED/
    ORDER_ID_STATUS_APPROVED) - обновляются сметы ПО ВСЕМ позициям заказа
    (RefreshEstimatesToOrder(ID, [], True));
  - иначе (черновик) - обновляются только позиции, попавшие в
    FItemsToEstimateChange - это позиции, которые были ВСТАВЛЕНЫ заново,
    либо у которых изменилось поле, помеченное тегом "est" в описании
    грида (Frg1.Opt.SetFields в TFrmOWOrder.PrepareFrgItems) - в частности,
    поле qnt (количество) помечено этим тегом, поэтому просто изменение
    количества в заказе-черновике ТОЖЕ вызывает пересинхронизацию сметы
    именно этой позиции (но см. 1.7 - это не значит запись в лог).

Таким образом сохранение заказа МОЖЕТ трогать сметы позиций, которые
пользователь напрямую не редактировал - просто потому что заказ уже
запущен/утверждён и обновляются все позиции, либо потому что qnt помечен
как "est"-поле.


1.4. TOrders.RefreshEstimatesToOrder и TOrders.LoadEstimate
--------------------------------------------------------------
RefreshEstimatesToOrder проходит по позициям заказа и для каждой вызывает
LoadEstimate(..., Silent=True, ...):
  - настоящее стандартное изделие (std=1)              - как раньше,
    копирование из сметы-эталона стандартного изделия;
  - нестандартное, НЕ purchase (resale<>1):
      - если формат нового (26) заказа И тип заказа П либо О
        (LUseStdLikeEstimate=True; для ПФ - НЕ применяется, там всегда
        старое поведение) И у позиции есть id_std_item (значит, привязана
        к группе -1/-2) - вызывается LoadEstimate с
        ForceEstimateFromStdItem=True: смета копируется из сметы-эталона
        стандартного изделия (группы -1 для П, -2 для О), а не
        пересчитывается по количеству;
      - иначе (старый формат либо ПФ) - QntChanged=True: состав сметы не
        трогается, просто пересчитываются количества (qnt/qnt_itm) по
        текущему количеству позиции в заказе (p_CorrectEstimateQnt).
  - изделие Д/К (resale=1, покупное) - обычная загрузка по наименованию.

LoadEstimate (uOrders.pas) - универсальная точка входа что для сметы
стандартного изделия (IdStdItem<>null), что для сметы позиции заказа
(IdOrderItem<>null). Ключевой момент для нового (26) формата: для
НЕСТАНДАРТНОГО изделия типа П (std=0, ParentIdStdItem указывает на группу
-1) интерактивное редактирование сметы позиции заказа (когда пользователь
кликает "Смета" в гриде заказа) ПЕРЕНАПРАВЛЯЕТСЯ на редактирование сметы-
эталона стандартного изделия (той самой группы -1) - то есть открывается
и правится ДРУГАЯ запись estimates (id_std_item=..., id_order_item=null),
а не смета самой позиции заказа. Синхронизация из отредактированного
эталона В САМУ позицию заказа (копированием) происходит ОТДЕЛЬНО, только
при следующем сохранении заказа, через RefreshEstimatesToOrder (см. 1.3) -
НЕ сразу после сохранения диалога сметы эталона.
Для типа О - наоборот, редиректа нет: смета уже скопирована автоматически
(из группы -2) и открывается только на просмотр (LReadOnlyEstimate).
Внутри RefreshEstimatesToOrder этот редирект НЕ применяется
(ForceEstimateFromStdItem=True отключает его) - там как раз и нужно
скопировать смету-эталон в позицию заказа, а не открыть сам эталон.

Если у стандартного изделия (группы -1) ещё вообще нет сметы-эталона (то
есть пользователь её ни разу не заполнял) - LoadEstimate выходит без
всякого действия (ни в диалоговом, ни в тихом режиме) - копировать
реально нечего (правка от 05.09.2026 - раньше в тихом режиме создавалась
"фантомная" пустая запись сметы позиции заказа, см. раздел "Известные и
исправленные проблемы" ниже).


1.4a. Насколько строго "копия" совпадает с "эталоном"
-----------------------------------------------------------
По составу - да, полностью: p_copy_std_estimate_to_order_item (d_estimates.sql)
построчно копирует из эталонной сметы в позиционную группу, наименование, единицу,
qnt1/qnt1_itm (количество НА ЕДИНИЦУ изделия) и ссылку id_or_std_item/or_std_item_cnt
БЕЗ ИЗМЕНЕНИЙ, а вот итоговые qnt/qnt_itm пересчитывает как qnt1 * количество_в_заказе
(ceil до 3 знаков). То есть единственное отличие копии от эталона - количество,
пересчитанное на количество этой позиции в заказе; перечень и состав позиций сметы
всегда идентичны эталону НА МОМЕНТ последнего копирования.

Но "всегда" здесь означает "по состоянию на последнее сохранение заказа", а не
непрерывно: копирование происходит только внутри RefreshEstimatesToOrder, то есть при
сохранении заказа (см. 1.3-1.4). Если эталон отредактировали, а заказ после этого ещё
не пересохраняли - копия в позиции заказа физически устарела и отличается от эталона,
пока заказ не сохранят снова.

Модель "эталон + копия в позиции заказа" действует ТОЛЬКО для нестандартных изделий
нового (26) формата типа П и О (и для настоящих стандартных изделий, где "эталон" -
это сама запись стандартного изделия в справочнике). У нестандартных изделий СТАРОГО
формата этой модели нет вообще - там единственная смета, привязанная прямо к позиции
заказа, которую пользователь редактирует непосредственно (состав задаётся вручную,
при сохранении заказа лишь пересчитывается итоговое количество - QntChanged).
Для типа ПФ (полуфабрикат) запись-эталон (группа -3) в справочнике заводится так же,
как для П/О (см. 1.2), но принудительное копирование из неё в RefreshEstimatesToOrder
НЕ включено - LUseStdLikeEstimate явно исключает STDITEM_TYPE_SEMIPRODUCT (uOrders.pas,
строка ~635) - то есть для ПФ по-прежнему работает только старый пересчёт количества,
эталон существует, но никуда автоматически не копируется. Похоже на недоделанный до
конца кусок функциональности, а не осознанное решение - явного объяснения в коде нет,
стоит уточнить у разработчика при случае, не является ли это отдельным дефектом.

И ещё один нюанс: для нестандартных изделий нового формата (что П, что О) сама копия в
позиции заказа НИКОГДА не редактируется пользователем напрямую - кнопка "Смета" на
позиции заказа либо перенаправляет на эталон (тип П, см. 1.4), либо открывает копию
только на просмотр (тип О). Ручное редактирование состава всегда происходит на уровне
эталона (группа -1/-2 в справочнике стандартных изделий), а не на уровне позиции
заказа - позиция заказа только принимает то, что туда скопируют при сохранении заказа.


1.4b. Немедленная синхронизация копии сметы позиции заказа (с 05.09.2026)
------------------------------------------------------------------------------
До этой правки собственная смета позиции заказа (копия, см. 1.1) для
нестандартного изделия типа П синхронизировалась с эталоном ТОЛЬКО при
следующем сохранении заказа целиком (TOrders.RefreshEstimatesToOrder, см.
1.4). То есть если открыть смету из журнала заказов (что реально означает
правку эталона, группа -1 - см. 1.4), отредактировать и сохранить, а сам
заказ при этом НЕ пересохранять - собственная копия в позиции заказа
оставалась старой/пустой до следующего сохранения заказа. Для
нестандартного изделия, которое всегда создаётся для одной конкретной
позиции заказа, откладывать синхронизацию смысла не было - в отличие от
настоящих стандартных изделий, где эталон может годами жить и
редактироваться независимо от уже оформленных (и, возможно, уже
запущенных в производство по прежней версии сметы) заказов.

Исправлено: TOrders.LoadEstimate получил новый параметр
ASyncOrderItemAfterSave: Integer = 0 (id позиции заказа); в момент
редиректа для П (см. 1.4) в него передаётся id ИМЕННО ТОЙ позиции заказа,
из которой было инициировано редактирование. Это значение прокидывается в
TEstimateApplyContext.SyncOrderItemAfterSave, и сразу после успешного
сохранения самой сметы-эталона (внутри ApplyEstimateArray, ПОСЛЕ коммита
транзакции и записи в лог изменений) немедленно выполняется тот же самый
вызов, которым раньше синхронизация делалась только при сохранении заказа -
LoadEstimate(null, IdOrderItem, null, False, False, True, False, True)
(Silent=True, ForceEstimateFromStdItem=True) - копия в позиции заказа
обновляется мгновенно, а не при следующем сохранении заказа. Побочный
эффект: т.к. эта копия сохраняется через тот же ApplyEstimateArray, у неё
тоже сразу появляется своя запись в estimate_change_log (source='4' -
"обновление из сметы стандартного изделия"), не дожидаясь пересохранения
заказа - хотя в норме смотреть стоит именно историю эталона (см. 1.6).

Вызовы RefreshEstimatesToOrder (ForceEstimateFromStdItem=True) сам редирект
для П не проходят (см. условие "not ForceEstimateFromStdItem" в 1.4), так
что ASyncOrderItemAfterSave там всегда остаётся 0 - новая логика не мешает
штатной синхронизации при сохранении заказа и не создаёт рекурсии.

Нюанс: если по этому нестандартному П-изделию уже создан связанный
отгрузочный заказ (копия позиции с тем же id_std_item - группа -1 общая
для производственного и отгрузочных заказов, см. FCreateShipmentFromProductionId
в uFrmOWOrder.pas), немедленная синхронизация распространяется ТОЛЬКО на
ту позицию заказа, ИЗ КОТОРОЙ реально было инициировано редактирование (её
id и передан в ASyncOrderItemAfterSave) - а не на все позиции во всех
заказах, ссылающихся на тот же эталон. Позиции в остальных таких заказах
по-прежнему получат актуальную копию только при следующем сохранении
СВОЕГО заказа (см. 1.3-1.4) - это сознательное ограничение, чтобы не
трогать задним числом чужие (возможно, уже выполненные/отгруженные) заказы
одним лишь фактом правки эталона из другого заказа.


1.5. TOrders.ApplyEstimateArray - что именно сохраняется в БД
-----------------------------------------------------------------
Общая функция сохранения результата (что для эталона, что для позиции
заказа - определяется контекстом Ctx, собранным в LoadEstimate):
  - создаёт/обновляет саму запись estimates (dt всегда = сегодня, см. 1.7);
  - если Ctx.IsOrItemStd (копирование из эталона) - вызывает
    p_copy_std_estimate_to_order_item(эта_смета, эталонная_смета, кол-во) -
    если у эталона своей сметы ещё нет (id эталонной сметы = null),
    процедура просто ничего не копирует (не ошибка!) - тогда после неё
    p_DeleteFreeEstimate должна убрать образовавшуюся пустую запись (но
    с 05.09.2026 этот сценарий вообще не должен возникать, см. 1.4);
  - если Ctx.QntChanged - вызывает p_CorrectEstimateQnt (пересчёт
    количеств, состав не трогается);
  - иначе (ручной ввод/загрузка нестандартной сметы) - создаёт позиции
    через p_createestimateitem по массиву Est из диалога;
  - в конце - p_DeleteFreeEstimate(id сметы): удаляет саму запись
    estimates, если в ней НЕТ ни одной строки estimate_items и isempty
    не равен 1 (в т.ч. isempty is null - см. nvl-правку от 05.09.2026).


1.6. История изменений - estimate_change_log
-----------------------------------------------
Пишется через TOrders.LogEstimateChange(AIdEstimate, ASource, AChanges) -
вызывается из ApplyEstimateArray ПОСЛЕ успешного коммита, и только если:
  - AIdEstimate <> null, и запись в estimates всё ещё существует (не была
    удалена только что отработавшей p_DeleteFreeEstimate - иначе вставка
    строки в estimate_change_log упала бы по внешнему ключу, ORA-02291);
  - AChanges <> '' (BuildEstimateDiffText нашёл реальные отличия по
    составу/количеству на единицу - qnt1) ИЛИ ASource = '0' (это самая
    первая загрузка данной сметы - EstBefore.Count = 0 - тогда пишем лог
    даже при "пустом" диффе, как факт первичной загрузки).
  - ВАЖНО: это условие проверяется НЕЗАВИСИМО от Ctx.Silent - тихий вызов
    из RefreshEstimatesToOrder тоже пишет в лог, если реально что-то
    изменилось или это первая загрузка.
  - НЕ пишется вообще, если Ctx.QntChanged = True (чистый пересчёт
    количества по старой схеме - см. явный комментарий в коде).
  - Для нового (26) формата П/О пересчёт по ForceEstimateFromStdItem не
    ставит QntChanged, НО диффится по qnt1 (кол-во на единицу в эталоне),
    которое от количества В ЗАКАЗЕ не зависит - поэтому простое изменение
    количества позиции в заказе и тут не даёт диффа и не пишется в лог,
    хотя сама функция и вызывается.
  - source - список кодов через запятую (см. TEstDlgChannel.SourceUsed в
    uFrmOGedtEstimate.pas), расшифровка в SourceCodesToText
    (uFrmOWrepEstimateChanges.pas); '0' - первичная загрузка,
    '3'/'4' проставляются в LoadEstimate по EstLogSource := IIf(IsOrItemStd,
    '4', '3') - т.е. '4' для копирования из эталона (в т.ч. для настоящих
    стандартных изделий), '3' для прямого ввода/загрузки нестандартной
    сметы или правки эталона.

Просмотр истории - uFrmOWrepEstimateChanges.pas (открывается через
Wh.ExecDialog(myfrm_Rep_EstimateChanges, ..., AId, AAddParam) - из
справочника стандартных изделий (AddParam=1, AId=id стандартного изделия)
или из журнала заказов, позиции заказа (AddParam<>1, AId=id order_items)).
ИСПРАВЛЕНО (05.09.2026): раньше этот диалог (как и диалог просмотра сметы -
uFrmOGlstEstimate.pas, действие "Просмотр", myfrm_R_Estimate) резолвил
id_estimate НАПРЯМУЮ - "select id from estimates where id_order_item = :id"
для позиции заказа, без учёта редиректа для П (см. 1.4). Из-за этого при
открытии истории или просмотра ИЗ ЖУРНАЛА ЗАКАЗОВ по позиции нестандартного
П-изделия показывалась смета/история САМОЙ ПОЗИЦИИ ЗАКАЗА, а не эталона
(группа -1) - хотя реальное редактирование (клик "Смета" в гриде заказа)
идёт именно на уровне эталона - в результате история казалась пустой или
неполной, а просмотр сметы - пустым, до следующего сохранения заказа.
Добавлена общая функция TOrders.ResolveEstimateDisplayTarget(AIdOrderItem;
out AIdStdItem) - повторяет условие редиректа из LoadEstimate, но только
для определения ЦЕЛИ ПРОСМОТРА, без каких-либо действий с БД; используется
и в TFrmOWrepEstimateChanges.Prepare, и в TFrmOGlstEstimate.PrepareForm -
оба теперь при таком редиректе показывают именно эталон (с пометкой в
заголовке), и правки видны сразу, а не после сохранения заказа. Для
настоящих стандартных изделий (AddParam=1) и для нестандартных изделий
старого формата/типа О/ПФ поведение не менялось - редиректа там не было
и нет. См. также 1.4b - синхронизация собственной копии позиции заказа
теперь тоже происходит немедленно, а не только при сохранении заказа.


1.7. "Дата сметы" в журнале заказов - не то же самое, что история изменений
------------------------------------------------------------------------------
Столбец "дата сметы" в детальной таблице журнала заказов и v_order_items
в целом (v_order_items.dt_estimate = es.dt, d_orders.sql) - это просто
estimates.dt той сметы, что привязана к id_order_item данной позиции.
А estimates.dt проставляется в TOrders.ApplyEstimateArray БЕЗУСЛОВНО,
сегодняшним числом, при КАЖДОМ успешном сохранении этой сметы - включая
чистый пересчёт количества (QntChanged) и повторное копирование из
эталона без изменений состава. То есть "дата сметы" отвечает на вопрос
"когда в последний раз заказ сохранялся и синхронизация трогала смету
этой позиции", а НЕ на вопрос "когда состав сметы содержательно менялся" -
на второй вопрос отвечает именно история изменений (estimate_change_log,
см. 1.6), а не эта дата. Не стоит делать выводы об изменении состава
сметы только по изменившейся дате в журнале заказов.


1.8. Удаление заказа (с 05.09.2026)
---------------------------------------------------------
Кнопка/пункт меню "Удалить заказ" (константа mbtOrderDelete = 1004, TFrmOWOrder,
uFrmOWOrder.pas) - видна только в Mode=fEdit, не для шаблона, при наличии роли
rOr_D_Order_Del (см. SetButtons); дублируется и в заголовке диалога, и в меню грида
изделий заказа (FrgItemsButtonClick) - оба места вызывают один и тот же
TitleButtonClick(mbtOrderDelete). Поведение зависит от статуса заказа (id_status) на
момент нажатия:

- ORDER_ID_STATUS_DRAFT (заказ в оформлении) - ФИЗИЧЕСКОЕ удаление записи заказа из БД.
  После подтверждения ("Заказ будет удален безвозвратно. Продолжить?") выполняется
  delete from orders (TFrmOWOrder.DeleteOrderPhysically) в отдельной пакетной транзакции
  (Q.QBeginTrans(True)/Q.QCommitOrRollback) - все зависимые записи (order_items, estimates
  по id_order_item, order_changes, order_complaints, or_payments, orders_add и т.п.)
  удаляются каскадно, через on delete cascade у соответствующих внешних ключей. Это не
  идёт через общий механизм ChangeOrderStatus/Save (там нет физического удаления, только
  смена статуса) - перехватывается ОТДЕЛЬНО, в самом начале TitleButtonClick, до вызова
  ChangeOrderStatus. Если delete упадёт по внешнему ключу - транзакция откатится, ошибку
  покажет сам QExecSql, диалог заказа останется открытым. Из известных НЕкаскадных ссылок
  на order_items/orders: fk_j_tasks_order_item (j_tasks.id_order_item -> order_items.id)
  переведён (05.09.2026, вручную, отдельным --!go блоком в d_references.sql) на on delete
  set null - больше не блокирует удаление заказа. Остаются некаскадными (не блокируют
  удаление ТОЛЬКО если для заказа/его позиций нет ссылающихся строк):
  fk_j_tasks_order (j_tasks.id_order -> orders.id) и fk_order_item_route_item
  (order_item_route.id_order_item -> order_items.id) - для заказа, ещё не запущенного в
  работу, обычно пустые, но не гарантированно.
- ORDER_ID_STATUS_STOPPED (заказ Остановлен) - "мягкое" удаление: после подтверждения
  ("Заказ будет помечен как "Удаленный", и останется доступным для просмотра. Продолжить?")
  статус меняется на ORDER_ID_STATUS_DELETED и заказ сохраняется обычным порядком (см.
  ChangeOrderStatus, ветка Tag = mbtOrderDelete, и общий механизм в TitleButtonClick) -
  запись в БД не удаляется, заказ остаётся доступен для просмотра.
- Любой другой статус (Утверждён/Запущен/Отклонён/уже Удалён) - действие недоступно,
  выводится "Действие недопустимо для этого заказа!" (см. ChangeOrderStatus).

См. отдельно уже существовавшую (до этой правки) кнопку/тег mbtDelete (константа = 16,
общий фреймворковый "Удалить") - для заказа она либо не показывается вовсе, либо видна
только на этапе добавления/копирования ещё не сохранённого заказа (Mode in [fAdd, fCopy]) -
с уже существующим (сохранённым) заказом в разделе mbtOrderDelete не пересекается.


1.9. Экспорт и отправка паспорта заказа (ПЗ) при запуске/изменении заказа (с 05.09.2026)
---------------------------------------------------------
Перенесена (портирована) логика TDlg_Order.ExportPassportToXLSX в новый диалог заказа
TFrmOWOrder - вызывается из SetTaskForServer (создание задачи для серверного процесса),
по тому же месту, что и в старом диалоге, но с БОЛЕЕ ИЗБИРАТЕЛЬНЫМИ условиями создания
файла (сам экспорт использует уже существующий общий метод Orders.ExportPassportToXLSX,
uOrders.pas, - никакой новой логики формирования содержимого паспорта не писалось):

- при ПЕРЕХОДЕ статуса заказа в ORDER_ID_STATUS_STARTED (Запущен) - паспорт создаётся
  (Orders.ExportPassportToXLSX(ID, LOrderPath, False, True)) и отправляется БЕЗУСЛОВНО,
  как и раньше в TDlg_Order;
- если заказ УЖЕ был в статусе Запущен и сохраняется снова (остаётся Запущен) - паспорт
  пересоздаётся, ТОЛЬКО если среди фактически изменившихся полей заказа есть хотя бы одно,
  используемое в шаблоне паспорта (тег вида #имя_поля# в самом файле шаблона). Если ни одно
  изменившееся поле не встречается в шаблоне - файл не создаётся вообще (и, соответственно,
  не будет вложен/скопирован в задачу серверным процессом при этом сохранении).

Определение набора тегов шаблона - TFrmOWOrder.NeedPassportExport (uFrmOWOrder.pas):
- набор тегов шаблона читается функцией GetXlsxTemplateTags(FileName) (uExcel2.pas,
  новая) - сканирует ПЕРВЫЙ лист файла шаблона (Module.GetReportFileXlsx('ПЗ')) через
  LibXL (без реального Excel - быстро, в отличие от Orders.ExportPassportToXLSX, который
  использует медленную COM-автоматизацию Excel через uExcel.pas/TA7Rep), ищет во всех
  текстовых ячейках подстроки вида #имя# и возвращает уникальный список найденных имён
  (без решёток, в нижнем регистре). Если файл шаблона не найден/не открылся - возвращается
  пустой массив, и NeedPassportExport на всякий случай считает, что паспорт нужен создать
  (т.е. отсутствие информации о тегах трактуется в пользу пересоздания файла);
- список ИЗМЕНИВШИХСЯ полей заказа берётся из уже существовавшей GetOrderChangedfieldNames
  (шапка заказа, тег 'chg' в DefineFields) и из новой TFrmOWOrder.GetItemsChangedFieldNames
  (табличная часть - грид изделий, тег 'chg' у колонок грида, аналогично существовавшей
  GetItemsChangesText). В шаблоне ПЗ таблица изделий представлена ОДНОЙ повторяющейся
  строкой (один и тот же набор тегов для всех позиций), поэтому проверка ведётся по
  объединённому (по всем строкам грида) списку изменившихся полей, без разбора по позициям;
- особый случай - добавление или удаление позиций в гриде изделий (сама структура таблицы
  меняется, а не значение конкретного поля) - GetItemsChangedFieldNames в этом случае
  добавляет в список фиктивное имя '*', которое NeedPassportExport трактует как изменение
  ВСЕГДА (безусловно требует пересоздания паспорта), независимо от набора тегов шаблона.

Отключаемая проверка - константа PASSPORT_EXPORT_ONLY_IF_TEMPLATE_FIELDS_CHANGED
(uFrmOWOrder.pas, = True по умолчанию). Если поставить в False - проверка по тегам
полностью отключается, и паспорт пересоздаётся и отправляется при КАЖДОМ сохранении
заказа в статусе Запущен, независимо от того, что именно изменилось (прежнее, безусловное
поведение, как в TDlg_Order) - оставлено на случай проблем с определением набора тегов.
На переход самого статуса в Запущен эта константа не влияет - паспорт создаётся и
отправляется в этом случае в любом случае, константа касается только повторных сохранений
уже Запущенного заказа.

ВАЖНЫЙ ПРИНЯТЫЙ КОМПРОМИСС (проговорено с пользователем явно): если в конкретном
сохранении паспорт не пересоздаётся (условия не сработали), временного файла паспорта не
будет, и серверный процесс НЕ включит вложение в рассылку в этот раз, даже если файл
паспорта в каталоге заказа на сервере уже существует с прошлого раза (актуальный, но
старый файл просто не пересылается повторно). Идеальным решением было бы: пересоздавать
файл только при изменении используемых полей, но ВСЕГДА отправлять/прикреплять уже
существующий файл (пересозданный или нет) - но это потребовало бы переделки самого
серверного процесса рассылки, что явно вынесено за рамки данной задачи.

Явно НЕ входит в эту правку (по решению пользователя, отдельная задача на будущее):
полный перевод самого экспорта паспорта (Orders.ExportPassportToXLSX) с медленной
COM-автоматизации Excel (uExcel.pas/TA7Rep) на быструю запись через LibXL (uExcel2.pas) -
в uExcel2.pas на данный момент реализовано только ЧТЕНИЕ (включая GetXlsxTemplateTags),
запись через LibXL ранее была начата и заброшена (см. закомментированный код в конце
файла) и не используется.

редактора сметы с текстовым названием типа изделия (см. выше) обнаружилось, что для настоящего

слеш/наименование/кол-во) - баг был скрыт до появления шапки редактора. Исправлено - в обеих вью
CASE теперь проверяет s.id_or_format_estimates/i.id_or_format_estimates (сама группа) вместо
ee.id_format/fi.id_format.

2.1. Этапы прохождения заказа - order_item_stages (d_order_stages.sql)
-----------------------------------------------------------------
Таблица order_item_stages(id, id_order_item, id_stage, qnt, dt) хранит
датированные записи о прохождении каждой позиции заказа (order_items)
через этапы обработки. id_stage:
  - 1 - в производство;
  - 2 - приёмка на СГП;
  - 3 - отгрузка с СГП;
  - 4 - приёмка на ОТК.

Триггер trg_order_item_stages_biud_r поддерживает order_items.qnt_to_sgp
(кэшированную нарастающую сумму по этапу 2 - приёмке на СГП) и пишет в
P_ToUchetLog.

Представления: v_order_items_for_stages (базовая выборка) ->
v_order_item_stages1 (по каждой позиции заказа - количества/даты/статус по
всем 4 этапам через коррелированный pivot на sys_context) ->
v_order_stages1 (по заказу в целом - агрегирование статусов позиций через
F_GetOrderStage_State, которая сворачивает min/max статусы позиций в
null/0/1/2 - "не начат"/"частично"/"завершён").

Процедуры:
  - p_OrderStage_SetMainTable(IdOrder, IdStage) - при полном завершении
    этапа 2 или 3 по всем позициям заказа проставляет orders.dt_to_sgp
    (этап 2) или orders.dt_from_sgp (этап 3);
  - p_OrderStage_SetItem(IdOrderItem, IdStage, NewDt, NewQnt,
    UpdateOrders, out ResQnt, Adding=0) - устанавливает/добавляет/удаляет
    одну датированную запись, ограничивая количество остатком, ещё не
    принятым/отгруженным по данной позиции; при UpdateOrders=True в конце
    вызывает p_OrderStage_SetMainTable.

В этом же файле присутствует более старый и, по всей видимости,
частично не используемый механизм ОТК (order_otk/v_order_otk_items,
завязанный на внешнюю схему uchet.), а также много не относящегося к СГП
легаси-содержимого (material_groups, order_smeta, order_otk,
delayed_prod_reasons, or_montage и т.п.) - в анализ задачи по СГП это не
входит.

Флаг order_items.sgp (число(1), "отгрузка позиции с СГП") -
используется в ряде статусных вычислений v_order_item_stages1 как
исключающий признак (case when not(nvl(i.sgp,0) = 1 ...)) - позиции без
этого флага не участвуют в учёте СГП по старому формату.


2.2. Динамический расчёт остатков по стандартным изделиям - d_sgp.sql
-----------------------------------------------------------------
Отчёт "Текущее состояние СГП" (стандартные изделия) считается
динамически, без хранения остатков - на каждый показ заново
пересчитывается вся цепочка представлений.

Ключевые принципы (из заголовочного комментария файла):
  - учитываются только стандартные изделия, у которых в or_std_items
    установлен by_sgp = 1 - причём этот флаг должен стоять ТОЛЬКО на
    отгрузочных (сбытовых) форматах; если ошибочно проставлен на
    производственном - учёт по этому формату будет неверным;
  - "запущено в производство" определяется по orders.id_organization = -1;
    любая другая организация - это заказ клиента (отгрузка);
  - сопоставление производственного и отгрузочного изделия делается
    ТОЛЬКО ПО ИМЕНИ (or_std_items.name) - в комментарии к файлу прямо
    сказано, что предполагается (но никак не проверяется), что у каждой
    группы есть ровно один производственный и один сбытовой подформат;
  - формат КБ РЦ из этого механизма явно исключён;
  - нестандартные изделия (nstd=1) полностью исключены из этого
    механизма сопоставления по имени - для них отдельная параллельная
    логика (см. 2.3).

Цепочка представлений: v_order_items_all/v_order_items__ ->
v_sgp_sell_formats -> v_sgp_sell_items (список отслеживаемых изделий) ->
v_sgp_by_psp_sell(_list)/v_sgp_by_psp_prod(_list) (всего когда-либо
заказано/запущено) -> v_sgp_registered(_list)/v_sgp_shipped(_list)
(фактическое движение, из order_item_stages, этапы 2/3, с фильтром
dt > sgp_params.dt_beg) -> v_sgp_shipped_plan(_list)/v_sgp_in_prod(_list)
(план/в работе, для ещё не закрытых заказов) -> v_sgp_move_list (полный
аудит движения - UNION событий по паспортам производства/отгрузки и по
актам) -> v_sgp_items (итоговая агрегация: qnt = registered + act_in -
shipped + act_out; плюс qnt_need и цена/сумма через v_sgp_item_prices,
которая берёт себестоимость сырья из сметы соответствующего
производственного изделия - ИТМ).

Таблица sgp_params (одна строка) хранит дату отсечки (сейчас 01.08.2024) -
движение по стадиям учитывается только после этой даты.


2.3. Параллельный учёт нестандартных изделий - v_sgp2 ("Розница")
-----------------------------------------------------------------
Для нестандартных изделий (nstd=1) сопоставление по имени невозможно
(имена, как правило, уникальны и не парны), поэтому используется
отдельный, более простой механизм - учёт не по имени/группе, а
непосредственно по позиции заказа (по "слешу"):

v_sgp2_order_items (все order_items с nstd=1) -> v_sgp2 (агрегация по
каждой ПОЗИЦИИ ЗАКАЗА - количества этапов 2/3 из order_item_stages плюс
акты, с фильтром id_or_format_estimates = 0, то есть только "старые"
плоские нестандартные изделия без деления на группы -1/-2/-3, см. 1.2).

Отчёт по нестандартным изделиям ("Состояние СГП (нестандартные
изделия)") использует именно v_sgp2 и открывается как myfrm_Rep_Sgp2 -
обрабатывается универсальным uFrmXGlstMain.pas (не отдельным юнитом).


2.4. Ревизия СГП - уже существующий механизм актов инвентаризации
-----------------------------------------------------------------
uFrmOGedtSgpRevision.pas (диалог "Ревизия СГП", открывается и для
стандартных - grid на v_sgp_items, и для нестандартных изделий - grid на
v_sgp2, в зависимости от ID = 0/<>0) - это уже готовый, работающий
механизм актов инвентаризации:
  - показывает расчётное количество (qnt, из v_sgp_items/v_sgp2) рядом с
    полем для ввода фактического количества по пересчёту (qnt_fact);
  - при сохранении (TFrmOGedtSgpRevision.Save) по каждой позиции с
    заполненным qnt_fact считает разницу qnt_fact - qnt; положительные
    расхождения собираются в один акт оприходования (sgp_act_in +
    sgp_act_in_items), отрицательные - в один акт списания (sgp_act_out +
    sgp_act_out_items), оба - одной транзакцией (Q.QBeginTrans/
    QCommitOrRollback);
  - элементы актов ссылаются либо на id_std_item (стандартные изделия),
    либо на id_or_item (нестандартные, = order_items.id) - выбор
    определяется тем же условием ID = 0;
  - явно указано пользователю: "скорректировать либо отменить ревизию и
    созданные по ней акты нельзя".

Таким образом, идея "выгрузить текущее состояние в акт инвентаризации и
учитывать его" технически уже реализована как работающий инструмент - её
нужно не изобретать заново, а переиспользовать (в том числе вызывая
создание таких актов также из диалогов приёмки/отгрузки с СГП по старым
заказам, с комментарием о заказе-источнике).

2.6. Дискриминаторы старого и нового формата заказов
-----------------------------------------------------------------
  - СТАРЫЙ формат: orders.id_organization = -1 отмечает "производство"
    (запуск), любое другое значение - заказ клиента/отгрузка;
  - НОВЫЙ формат: orders.std_item_type (0 = STDITEM_TYPE_PRODUCTION,
    1 = STDITEM_TYPE_SHIPMENT, 2 = STDITEM_TYPE_SEMIPRODUCT,
    проставляется из or_format_estimates.type, см. 1.2);
  - граница между форматами по времени - константа cOrderNew26TypeID =
    18510 (uOrders.pas) - id заказа в схеме Учёта, начиная с которого
    заказ считается "новым (26)" форматом (id < 18510 - старый).

Существенное отличие, напрямую относящееся к предлагаемой переделке:
в НОВОМ формате производственное и отгрузочное нестандартные изделия
УЖЕ гарантированно создаются парой с одинаковым именем - см. 1.2,
p_create_or_std_item_nonstandard_new_format создаёт сразу две записи
or_std_items (группы -1 и -2) с общим именем при создании
производственного нестандартного изделия. Это значит, что для нового
формата и для нестандартных изделий тоже можно применить сопоставление
"по имени и группе", как для стандартных - то есть предлагаемое единое
правило ("чёткое поступление/отгрузка изделий, совпадающих по имени и
параллельных по группе") для нового формата уже имеет техническую основу
в структуре данных, тогда как в СТАРОМ формате нестандартные изделия
такой парности не имеют в принципе (отсюда и существующий обходной путь
через v_sgp2 - учёт по позиции заказа/слешу, а не по имени).

2.8. Ход переделки СГП (обновляется по мере реализации)
-----------------------------------------------------------------
Уточнения от пользователя, положенные в основу переделки:
  - "группа" = or_formats (id_or_formats), "подгруппы" = or_format_estimates/
    or_std_items внутри неё (одна производственная, одна или несколько
    отгрузочных; в старых форматах бывает и несколько производственных).
    Сейчас (v_sgp_items) остаток считается отдельно по каждой отгрузочной
    подгруппе - если у группы несколько отгрузочных подгрупп с by_sgp=1,
    один и тот же физический товар даёт несколько отдельных строк остатка.
    Новая логика считает по ИЗДЕЛИЮ (имени), просуммированному по всем
    отгрузочным подгруппам группы; в комбобоксе выбор - группа целиком, а
    не конкретная отгрузочная подгруппа. Для старых групп с несколькими
    производственными/отгрузочными подгруппами движения дальше не будет,
    но остаток на момент среза переносится так же - по имени, без разбивки
    по подгруппе.
  - Снимок текущего состояния - материализация в таблицу (не через
    sgp_act_in/out), старый диалог (uFrmOGrepSgp.pas) остаётся, но
    переводится в readonly.
  - Логика автосоздания актов при приёмке/отгрузке старых заказов
    выносится в одну хранимую процедуру (единая точка входа).
  - Нестандартные изделия - ТОЛЬКО снимок (просмотр прошлого состояния),
    без ongoing-актов: новые нестандартные изделия нового формата никак не
    пересекаются со старыми, поэтому ни начальное состояние, ни
    промежуточные акты инвентаризации по ним не нужны - в отличие от
    стандартных, где физический остаток на складе общий для старых и
    новых заказов и требует непрерывного учёта на переходный период.
  - Порог старый/новый заказ - как и раньше, по cOrderNew26TypeID.
  - Цена/себестоимость в замороженном (readonly) отчёте - показывается
    так же, как сейчас (фиксируется в снимке на момент среза).
  - Новая логика "Текущее состояние СГП" для новых заказов - отдельный
    новый модуль (не правка uFrmOGrepSgp.pas), интерфейс может отличаться.
  - Нестандартные изделия в новом (26) формате - тоже отдельный отчёт
    (не тот же грид, что стандартные): ключевое отличие от стандартных -
    изделие встречается строго один раз в одном заказе (агрегация по
    заказам не нужна, в отличие от стандартных, где одно и то же изделие
    может заказываться многократно).

Сделано (07.09.2026, d_sgp.sql):
  - Таблица sgp_snapshot_std_items - снимок остатка по стандартным
    изделиям на момент среза, ключ (id_or_formats, item_name), полный
    набор разрезов (как сейчас в v_sgp_items: заказано/запущено/принято/
    отгружено/план/потребность/цена/сумма/цена и сумма по смете).
  - Таблица sgp_snapshot_nstd_items - снимок по нестандартным изделиям
    старого формата, ключ - id_order_item (без агрегации по имени, т.к.
    нестандартное изделие уникально для своего заказа), полный набор
    разрезов, как в v_sgp2 (заказано/в производстве/принято/отгружено/
    остаток/цена/сумма/даты).
  - Представления v_sgp_snapshot_std_items / v_sgp_snapshot_nstd_items -
    тонкие обёртки над таблицами снимков с именами колонок, совпадающими
    с текущими полями грида (format_name, name и т.п.) - чтобы в Delphi
    можно было просто переключить SetTable на снимок, почти не трогая
    список колонок.
  - v_sgp_revisions переопределено на группу (or_formats) вместо
    отгрузочного подформата - т.к. readonly-отчёт выбирает группу целиком.
    Колонка id_format в выдаче теперь = id группы; фильтр в
    uFrmXGlstMain.pas (myfrm_J_Sgp_Acts) не менялся, он как принимал
    числовой параметр, так и принимает - просто теперь это id группы.
  - Представление v_sgp_items_by_group - агрегация тех же данных, что и
    v_sgp_items, но по (id_format, name), т.е. по ГРУППЕ, а не по
    отгрузочному подформату. НЕ построено как простой group by поверх
    v_sgp_items - часть его колонок (заказано/запущено/принято/отгружено/
    план) уже посчитана на уровне группы и одинаково повторяется на каждой
    строке-подформате (простой sum() умножил бы их на количество
    подформатов с этим именем), а часть (поправки по актам sgp_act_in/out)
    считана по конкретному id_std_item подформата и потому у дублей-строк
    отличается (sum() для них как раз нужен). Поэтому представление
    пересчитывает нужные компоненты заново от первичных данных (v_order_
    items__, order_item_stages, sgp_act_in_items/sgp_act_out_items),
    сразу сгруппированными по (id_format, name) - без прохода через
    v_sgp_items. Цена и цена по смете при нескольких отгрузочных
    подформатах с разной ценой на одноимённое изделие берутся средним -
    задокументированное упрощение для этого редкого/ошибочного случая.
  - Процедура p_Sgp_CreateSnapshot(PForce number default 0) - разово
    заполняет sgp_snapshot_std_items из v_sgp_items_by_group и
    sgp_snapshot_nstd_items из v_sgp2 (как есть, без изменения агрегации).
    Защищена от случайного повторного запуска (raise_application_error,
    если снимок уже есть и PForce <> 1) - т.к. повторный запуск после

Разобрано (07.09.2026, "странность" в uFrmOGedtDistributeQnt.pas -
почему сравнение по raw id_std_item там работает, хотя ожидалось, что
id_std_item у производственных и отгрузочных изделий всегда разный):
  Пользователь заметил, что диалог распределения количества (сопоставляет
  позиции заказа П и родственных ему заказов О, связанных через
  orders.id_production_order, по СЫРОМУ равенству id_std_item - см. код
  там, комментарий "сопоставление - по id_std_item, а НЕ по slash") на
  практике отработал нормально - что противоречило его же более раннему
  утверждению "он всегда должен быть разный".
  Разгадка нашлась в uFrmOWOrder.pas:
  - PrepareFrgItems (комментарий у строк 839-846): при автосоздании заказа
    О из заказа П (FCreateShipmentFromProductionId - ровно тот сценарий,
    с которым и работает диалог распределения, т.к. использует то же самое
    id_production_order) состав копируется из П как есть, "при простом
    копировании заказа... id_std_item не переопределяется - остаётся тем
    же, что и у источника".
  - SaveOrderItems (строки 3236-3295): блок пересчёта/переопределения
    id_std_item (создание нестандартного изделия или резолв в группу -2 -
    IsNameChanged/LForceResolveShpNstd) целиком находится под условием
    nstd=1 - т.е. касается ТОЛЬКО нестандартных изделий. Для стандартных

  Итог: для стандартных изделий в СЦЕНАРИИ "заказ О автосоздан из заказа П"
  id_std_item в order_items заказа О буквально совпадает с id_std_item

  поэтому сравнение по raw id_std_item в диалоге распределения работает
  верно, это не случайность, а следствие того, как устроено копирование.

  добавленных в заказ О самостоятельно через справочник (picker) - там

  Решение пользователя: диалог распределения количества (uFrmOGedtDistribute-
  Qnt.pas) НЕ трогаем, оставляем сравнение по raw id_std_item как есть - это

Проведено отдельное расследование в изолированной среде:

1. Побайтово сверена таблица кодов Code128 и алгоритм контрольной суммы в
   uBarcode128.pas с независимым эталоном - расхождений нет, наша
   генерация штрихкода не является причиной проблемы.

2. Через headless-браузер с подменой камеры на заранее подготовленное
   видео с идеально чётким штрихкодом (без реальной камеры, освещения,

   воспроизвести - то есть дело не в условиях съёмки.

   библиотеки ZXing в целом.

5. В исходном коде встроенной библиотеки ZXing (класс
   HTMLCanvasElementLuminanceSource, метод toGrayscaleBuffer) найден
   статический счётчик-переключатель (FRAME_INDEX), который инвертирует

   переключатель не используется вовсе, поэтому там всегда всё исправно.

   настоящий баг стороннего кода библиотеки ZXing, а не наша ошибка и не
   следствие условий съёмки.

Исправление в scan.html (функция startScan/decodeLoop): вместо штатного
reader.decodeFromConstraints(...), который отдаёт декодеру кадры прямо с

картинка. Разрешение камеры и непрерывный автофокус из прошлой правки
сохранены как есть - вреда от них нет, просто не они были причиной.

Исправление проверено в изолированной среде (headless-браузер + подмена

uServerTasks.pas / uScanApi.pas: резидентный сервер /scanapi - самообновление,
минутный планировщик задач, устранён зависавший exception при занятом порту
----------------------------------------------------------------------

Задача: переделать серверный процесс так, чтобы он работал без завершения, сам
проверял обновления (раз в 5 минут) и корректно восстанавливался после краша
через повторный запуск задачей планировщика (тоже раз в 5 минут). Также нужен
минутный таймер для задач с жёстко заданным в коде временем, без проверки
пересечений между ними.

Перед реализацией проверил Uchet.dpr и обнаружил, что единственность самого
резидентного процесса УЖЕ обеспечена мьютексом (CheckInstance в Uchet.dpr) -
имя мьютекса учитывает и модуль, и переданный параметр командной строки. Для
варианта "Сервер" ($IFDEF SRV) при не удавшемся захвате мьютекса программа
тихо завершается (Halt, без диалога). То есть если планировщик Windows будет
пытаться запускать "Сервер.exe /scanapi" каждые 5 минут - при уже работающем
резидентном сервере такие попытки будут сами по себе мгновенно и тихо
завершаться, а если резидентный процесс упал - именно такая попытка его и
поднимет заново. Ничего дополнительно для этого в коде писать не потребовалось,
важно только настроить сам повтор в планировщике заданий Windows (это делается
отдельно от кода, повторение задачи /scanapi каждые 5 минут).

Для проверки обновлений (по просьбе пользователя - "приспособить" приём из
uUpdater.pas) сделано так же, как там: сравнение даты изменения файла exe
(TFile.GetLastWriteTime) с той, что была на момент старта текущего процесса,
без обращения к updater.dir/Uchet_Updater.exe - тот функционал в uUpdater.pas
привязан к запуску из %LOCALAPPDATA%\Uchet\ и рассчитан на скачивание файлов
с сетевого ресурса, что для сервера, который сам пересобирается прямо в месте
запуска, не требуется - здесь просто нужно заметить, что файл на диске стал
новее, и корректно завершиться.

Добавлен новый класс TScanApiWatchdog (uServerTasks.pas) - создаётся только в
резидентном режиме (задача /scanapi), держит два TTimer:
  - раз в 5 минут - сравнивает дату файла exe с датой на момент старта, и если
    она изменилась - логирует, останавливает HTTP-сервер (ScanApi.Stop) и
    закрывает приложение (FrmMain.Close), как обычную задачу;
  - раз в минуту - вызывает новую процедуру TTasksS.MinutelyTasks (объявлена в
    интерфейсе TTasksS рядом с HourlyTasks, пока пустая - задачи с конкретным
    временем добавляются туда постепенно, по аналогии с HourlyTasks, без
    проверки пересечений между ними, как и просил пользователь).
Перенос уже существующих задач планировщика (/fromparsec, /turvreport и т.п.)
на MinutelyTasks НЕ делался - это отдельная постепенная работа, сейчас только
каркас механизма.

Попутно устранена реальная причина, из-за которой раньше пропадало
диагностическое окно сервера (см. более раннюю запись про алгоритм
взаимодействия телефона с сервером): TScanApi.Start вызывал
FHttpServer.Active := True без обработки исключений - если порт уже занят
(например, предыдущий процесс не успел до конца его освободить после аварийного
завершения), необработанное исключение просто зависало на диалоге madExcept,
который некому было закрыть. Теперь эта установка обёрнута в try/except: при
неудаче пишется причина в лог (Module.ToLogFile) и Start корректно возвращает
управление с Active = False, без исключения. TTasksS.Run в этом случае теперь
тоже штатно завершает процесс (раньше при таком сценарии осталось бы неясно,
что вообще происходит) - следующая попытка запуска той же задачи планировщиком
(через 5 минут) начнёт всё заново.

Компиляцию Delphi проверить не могу - только побайтовая проверка кодировки
(UTF-8 с BOM, только CRLF) и баланс begin/end/скобок с учётом комментариев.
Нужна проверка сборкой и реальным запуском на сервере.

Поправка: проверка обновлений резидентного сервера - без прямой перезаписи
работающего exe
----------------------------------------------------------------------

Пользователь поправил предыдущий вариант (сравнение даты файла exe с самим
собой на момент старта процесса): прямая перезапись исполняемого файла уже
запущенного приложения приводит к краху, так делать нельзя. Правильный подход -
как в uUpdater.CheckForUpdatesAndRunUpdater, эта инфраструктура (Updater\
updater.dir рядом с exe, сравнение с копией на сервере, сам обновлятор
Uchet_Updater.exe) уже есть и рассчитана именно на безопасную замену файла:
обновлятор запускается ОТДЕЛЬНЫМ процессом и дожидается закрытия обновляемого
файла, прежде чем его подменить.

Переделано: в uUpdater.pas добавлены три самостоятельные функции (без побочных
эффектов вроде MessageBox/Halt внутри самой проверки - они бы зависли на
headless-сервере) - GetUpdateServerBasePath (чтение updater.dir),
IsExeUpdateAvailable (сравнение дат exe с копией на сервере) и
RunUpdaterAndHalt (синхронизация папки Updater, запуск Uchet_Updater.exe с
текущими параметрами командной строки, Halt(0)). Сама функция
CheckForUpdatesAndRunUpdater (используется остальными, клиентскими модулями)
не тронута - расчитанный риск не трогать уже проверенную клиентскую логику.

TScanApiWatchdog.UpdateCheckTimerTimer (uServerTasks.pas) переписан: вместо
сравнения даты своего же файла с самим собой теперь читает Updater\updater.dir
рядом с exe сервера, сравнивает с копией на сервере (через новые функции выше),
и при наличии обновления - останавливает HTTP-сервер (ScanApi.Stop), запускает
Uchet_Updater.exe (RunUpdaterAndHalt - сам делает Halt(0) при успехе) и таким
образом закрывается; если запуск обновлятора не удался (например, нет
Uchet_Updater.exe рядом) - логирует ошибку и восстанавливает работу сервера
(ScanApi.Start), чтобы не остаться в подвешенном состоянии до следующей
попытки через 5 минут.

Предполагаю (не проверено, т.к. не вижу сервер живьём), что рядом с серверным
exe (там, где он реально запускается) уже есть своя папка Updater с
updater.dir, по тому же принципу, что и у клиентских модулей в
%LOCALAPPDATA%\Uchet\Updater\ - если это не так и такой папки там нет,
IsExeUpdateAvailable просто не будет находить обновлений (GetUpdateServerBasePath
вернёт False), и эта часть работать не будет, пока эта папка не появится.

Сервер (uServerTasks.pas, uFrmMain.pas, Uchet.dpr): сервер стал полностью
резидентным для ВСЕХ задач, не только для сканирования штрихкодов.

Уточнение от пользователя: предыдущая реализация (см. предыдущую запись
выше) была слишком узкой - резидентным был сделан только /scanapi, а
остальные задачи (/fromparsec, /hourly и т.п.) по-прежнему завершали
процесс сразу после выполнения. Правильное намерение - сервер целиком
(независимо от того, с каким параметром командной строки он запущен)
работает резидентно неограниченно долго и никогда не завершается сам
после разовой задачи.

Изменения:

1) TTasksS.Run (uServerTasks.pas) теперь всегда запускает ScanApi.Start
   (сканирование штрихкодов работает всегда, независимо от параметра
   запуска - конфликтов по доступу к БД с прочими задачами нет, это
   подтверждено пользователем), выполняет разовую задачу по параметру
   через новую функцию TTasksS.ExecuteTaskByName, и создаёт
   TServerWatchdog - процесс НИКОГДА не закрывается сам (FrmMain.Close
   больше не вызывается).

2) TTasksS.ExecuteTaskByName(ATaskName: string): Boolean - разовая задача
   вынесена из Run в отдельную функцию, чтобы её можно было использовать
   и при старте, и при выполнении задания вручную (см. п. 6). Ошибка
   внутри задачи логируется (см. п. 4) и не прерывает работу резидентного
   процесса.

3) TScanApiWatchdog переименован в TServerWatchdog (класс теперь отвечает
   не только за сканер штрихкодов, а за весь резидентный сервер) и
   расширен: его минутный таймер теперь дополнительно -
   - проверяет соединение с БД (Q.Connected) - при потере соединения
     процесс сразу завершается (Halt), т.к. без БД не может работать ни
     сканирование, ни прочие задачи; следующая попытка - через 5 минут по
     сторожевому заданию планировщика;
   - в начале каждого часа (MinuteOf(Now) = 0) вызывает
     TTasksS.HourlyTasks - таким образом, часовые задачи теперь тоже
     запускаются из общего минутного таймера резидентного процесса, а не
     отдельным заданием планировщика "/hourly" (хотя это задание пока не
     удалено - см. заголовок uServerTasks.pas, миграция постепенная);
   - вызывает TTasksS.MinutelyTasks (без изменений в самом механизме);
   - и то и другое выполняется, только если разрешено расписание (см. п.5).

4) Логирование: добавлена LogTaskEvent(ItemName, Comment) - пишет
   одновременно и в файловый лог (Module.ToLogFile), и в БД (таблица
   adm_db_log через уже существующий метод TmyDBOra.QLog). Добавлена
   RunLoggedTask(TaskName, TaskProc: TProc) - выполняет переданную
   процедуру, логирует результат (выполнено/ошибка) через LogTaskEvent, и
   ошибка НЕ прерывает работу - используется для КАЖДОЙ отдельной
   процедуры внутри TTasksS.HourlyTasks (например, все ~18 отчётов в блоке
   8 часов утра теперь логируются индивидуально, а не одной строкой на
   всю пачку). Это решение одновременно закрывает два пожелания
   пользователя: обязательное логирование ошибок, и "если найдёшь иное
   решение [чем крах приложения через мадэксцепт] - отлично" - здесь
   ошибка одной задачи не приводит к падению всего резидентного процесса
   (и не мешает сканеру штрихкодов). Глобальный перехват необработанных
   исключений (madExcept, с завершением процесса) остаётся как
   дополнительная защита на случай ошибки вне этих обработчиков - это
   осталось приемлемым для пользователя, процесс перезапустится по
   сторожевому заданию планировщика.

5) Режим разработки: при наличии файла "dev" (Module.DevFileExists) при
   старте TTasksS.Run выводится вопрос (MyQuestionMessage) - выполнять ли
   задания по расписанию; ответ сохраняется в IsScheduleEnabled и
   проверяется в TServerWatchdog перед вызовом HourlyTasks/MinutelyTasks.
   Сканирование и проверка обновлений от этого флага не зависят.

6) Выполнение задания вручную: в TFrmMain (uFrmMain.pas) добавлен пункт
   главного меню "Выполнить задание..." (раздел {$IFDEF SRV}, виден
   всегда, не только в режиме разработки) - запрашивает имя задания
   (InputBox) и вызывает TasksS.ExecuteTaskByName, показывая результат.

7) Uchet.dpr: мьютекс единственности процесса для модуля Сервер (CheckInstance)
   изменён - раньше имя мьютекса учитывало параметр командной строки
   (что было нужно, пока разные параметры означали разные, независимо
   завершающиеся задачи); теперь, когда весь модуль резидентен независимо
   от параметра, имя мьютекса общее для модуля целиком (как и для
   остальных, не-серверных модулей) - иначе процессы, запущенные с разными
   параметрами, могли бы работать резидентно одновременно, дублируя
   выполнение задач и конкурируя за порт сканера штрихкодов. Проверка
   ParamCount = 1 (обязателен ровно один параметр) не изменилась.

Не сделано в этом раунде (оставлено на усмотрение пользователя, т.к.
явно только пользователь может расставить конкретное время): перенос
конкретных задач (/fromparsec, /turvreport и т.п.) с планировщика Windows
на жёстко заданное время внутри TTasksS.MinutelyTasks - процедура
специально оставлена пустой, с примером использования RunLoggedTask в
комментарии.


----------------------------------------------------------------------
Сервер (uServerTasks.pas, uFrmMain.pas): расписание задач переведено с
жёстко закодированных if-условий на декларативный массив с cron-подобным
расписанием и защитой от потерянных из-за просрочки запусков.

Уточнение от пользователя: не делать задания как ключи (строки вида
"/hourly", проверяемые вложенными if с HourOf(Now)/DayOfWeek(Date)), а
явно описывать задание как запись: краткое имя (на русском), необязательный
комментарий, выполняемая процедура, расписание в стиле cron. Обрабатывать
в минутном таймере по расписанию; если задача должна была выполниться, пока
выполнялась другая (запуск просрочен по этой причине, таких может быть
несколько), выполнять их после завершения предыдущей, в порядке нахождения
в массиве. Для ручного запуска - выбирать из заголовков (названий) заданий.

Реализация (uServerTasks.pas):

1) TScheduledTask - запись одной задачи расписания: Name (краткое имя на
   русском), Comment (необязательный), Cron (расписание, 5 полей через
   пробел - минута/час/день месяца/месяц/день недели, как в обычном cron:
   "*", списки через запятую, диапазоны "8-19", шаг "*/15" или "8-19/2"),
   Proc (TScheduledTaskProc = reference to procedure - сама задача).

2) CronFieldMatches/CronMatches - проверка, подходит ли конкретный момент
   времени под одно поле/под всё расписание целиком.

3) ScheduledTasks: array of TScheduledTask - само расписание, заполняется
   один раз при старте резидентного процесса функцией InitScheduledTasks.
   Сюда перенесены все задачи из прежней TTasksS.HourlyTasks - время каждой
   было и раньше жёстко задано в коде, здесь оно просто выражено через cron
   вместо вложенных if. Прежние часовые задачи -> "0 * * * *", задача в 4
   часа -> "0 4 * * *", пачка 8-часовых отчётов -> "0 8 * * *", задачи 1
   числа месяца -> "0 8 1 * *". Задачи "по понедельникам" оставлены с
   прежней проверкой DayOfWeek(Date) = 1 ВНУТРИ тела задачи (а не через
   поле дня недели в cron) - в модуле одновременно доступны DateUtils и
   SysUtils, у которых DayOfWeek может по-разному нумеровать дни недели, и
   чтобы не ошибиться при переносе, условие сохранено буквально таким же,
   как было в оригинале.
   Задачи, чьё время не было и раньше явно прописано в коде программы (перенос
   с параметров /fromparsec, /turvreport и т.п. - их время сейчас знает
   только планировщик Windows), в расписание пока НЕ добавлены - это
   отдельная, следующая работа.

4) ProcessScheduledTasks(AFrom, ATo) - проверяет расписание на каждую минуту
   диапазона [AFrom; ATo] (не только на текущую минуту) и выполняет
   совпавшие задачи строго в порядке их расположения в массиве
   ScheduledTasks - это и есть механизм защиты от просрочки: если минутный
   таймер не сработал вовремя (был занят выполнением предыдущей задачи),
   при следующем срабатывании AFrom/ATo захватывают весь пропущенный
   интервал, и ни одна задача, чьё время наступило за это время, не
   теряется. TServerWatchdog хранит FLastScheduleCheckMoment и передаёт в
   ProcessScheduledTasks диапазон от последней проверки до текущего момента.

5) TTasksS.ExecuteTaskByName: параметр командной строки "/hourly" убран -
   вся его нагрузка теперь в расписании и выполняется резидентным процессом
   сама, без внешнего запуска.

6) Для ручного запуска добавлены TTasksS.ScheduledTaskNames (имена всех
   задач расписания) и TTasksS.RunScheduledTask(индекс) (немедленное
   выполнение вне очереди). В uFrmMain.pas пункт меню "Выполнить задание..."
   переделан с ввода текста (InputBox) на выбор из списка - используется уже
   существующий в проекте диалог uFrmChooseDialog.TFrmChooseDialog.ShowDialog
   (радиогруппа, возвращает индекс выбранного варианта).

Не сделано в этом раунде (следующий шаг по мере необходимости): перенос
задач со старых параметров планировщика Windows (/fromparsec, /turvreport
и т.п.) в ScheduledTasks - для них ещё нет уже готового, однозначного
времени внутри кода программы, которое можно было бы просто выразить через
cron без риска что-то напутать.
